# AGENTS.md — план разработки Heroes of Rust

## Видение проекта

`Heroes of Rust` — пошаговая стратегия в духе `Heroes of Might and Magic`: игрок исследует карту приключений, собирает ресурсы, развивает города, нанимает армии, прокачивает героев и сражается в тактических пошаговых боях.

Цель первой версии — не повторить всю глубину HoMM, а создать небольшой вертикальный срез, в который уже можно играть.

## Главный принцип

Сначала делаем минимальную играбельную петлю:

1. Игрок управляет героем на карте.
2. Герой ходит по клеткам и тратит очки движения.
3. На карте есть ресурсы, город и нейтральный отряд.
4. Игрок собирает ресурс.
5. Игрок заходит в город и нанимает существ.
6. Игрок атакует нейтральный отряд.
7. Запускается простой пошаговый бой.
8. После победы игрок получает награду.
9. Ход заканчивается, начинается следующий день.

Все остальные системы добавляются только после того, как эта петля работает.

## Предлагаемый стек

### Язык

- Rust stable edition 2024 или актуальная stable edition, если 2024 недоступна в окружении.

### Игровой движок

Рекомендуемый стартовый вариант:

- `Bevy` — современный Rust ECS-движок, хорошо подходит для 2D/3D, прототипирования и модульной архитектуры.

Альтернативы:

- `macroquad` — проще для быстрого 2D-прототипа, меньше архитектурной сложности.
- `ggez` — простой 2D-фреймворк, но экосистема менее активна.

Для этого проекта по умолчанию выбираем `Bevy`, если не появится веская причина упростить стек до `macroquad`.

## Архитектурные правила

1. Игровая логика должна быть отделена от отображения.
2. Сначала проектируем данные и правила, затем визуализацию.
3. Основные системы должны быть детерминированными, чтобы позже было проще добавить сохранения, replay, AI и мультиплеер.
4. Не смешивать состояние карты приключений и состояние тактического боя.
5. Все крупные игровые сущности должны иметь стабильные ID.
6. Контент по возможности хранить в data-driven формате: `ron`, `json`, `toml` или `yaml`.
7. Не добавлять сложные фичи, пока нет работающего вертикального среза.

## Базовые игровые модули

### 1. Core/domain

Отвечает за чистую игровую модель без привязки к движку.

Сущности:

- `GameState`
- `Player`
- `Hero`
- `Army`
- `UnitStack`
- `UnitType`
- `Town`
- `ResourcePile`
- `AdventureMap`
- `Tile`
- `Position`
- `Faction`
- `ResourceBag`

Задачи:

- хранить состояние игры;
- валидировать действия;
- применять команды игрока;
- не зависеть от UI, графики и ввода.

### 2. Adventure map

Карта приключений.

Минимальная версия:

- прямоугольная сетка;
- типы клеток: земля, препятствие, вода/недоступно;
- герой занимает одну клетку;
- передвижение по клеткам;
- очки движения на день;
- объекты карты: ресурс, город, нейтральный отряд.

Позже:

- fog of war;
- дороги;
- зоны контроля;
- порталы;
- шахты;
- недельный прирост существ;
- генератор карт.

### 3. Town system

Города и найм армии.

Минимальная версия:

- один тип города;
- одно здание найма;
- один-два типа существ;
- недельный или дневной прирост;
- покупка существ за золото.

Позже:

- несколько фракций;
- дерево зданий;
- магическая гильдия;
- рынок;
- гарнизон;
- осады.

### 4. Hero system

Герои.

Минимальная версия:

- имя;
- позиция на карте;
- армия;
- очки движения;
- базовые характеристики: атака, защита, сила магии, знания — можно добавить позже, когда они реально понадобятся.

Позже:

- опыт и уровни;
- навыки;
- артефакты;
- заклинания;
- специализации.

### 5. Battle system

Тактический бой.

Минимальная версия:

- отдельное состояние боя;
- две стороны: атакующий и защитник;
- поле боя в виде сетки;
- стеки существ;
- очередность ходов;
- перемещение или атака;
- урон с простейшей формулой;
- победа при уничтожении всех стеков противника.

Простейшая формула урона на старт:

- `damage = attacker_count * unit_base_damage`
- убитые существа: `damage / defender_hp`, с учетом остаточного здоровья можно разобраться позже.

Позже:

- инициатива/скорость;
- контратака;
- мораль и удача;
- дальний бой;
- магия;
- препятствия;
- автобой;
- AI боя.

### 6. Economy

Минимальная версия:

- ресурс `gold`;
- сбор кучек золота на карте;
- стоимость найма существ;
- доход города в начале дня.

Позже:

- дерево, руда, ртуть, сера, кристаллы, самоцветы;
- шахты;
- рынок;
- обмен ресурсов.

### 7. Turn system

Минимальная версия:

- текущий день;
- активный игрок;
- кнопка завершения хода;
- восстановление очков движения героя;
- доход города.

Позже:

- неделя и месяц;
- события недели;
- несколько игроков;
- AI-ходы;
- hotseat.

### 8. AI

На раннем этапе AI не нужен.

Минимум после вертикального среза:

- нейтральные армии стоят на месте;
- в бою нейтральный стек атакует ближайшего врага.

Позже:

- AI для карты;
- оценка силы армий;
- захват объектов;
- планирование маршрута;
- стратегические цели.

### 9. UI/UX

Минимальная версия:

- отображение карты;
- выделение героя;
- отображение доступных ходов;
- панель ресурсов;
- кнопка завершения хода;
- простое окно города;
- простой экран боя.

Важно: UI не должен содержать бизнес-логику. Он отправляет команды в игровую модель и отображает результат.

## Предлагаемая структура проекта

На старте можно держать один crate, но сразу разделить код на модули:

- `src/main.rs` — запуск приложения и подключение плагинов/систем.
- `src/core/` — чистая модель и правила игры.
- `src/adventure/` — карта приключений и системы отображения/ввода.
- `src/battle/` — бой.
- `src/town/` — города.
- `src/ui/` — интерфейс.
- `src/data/` — загрузка игровых данных.
- `assets/` — спрайты, шрифты, карты, конфиги.

Если проект вырастет, можно перейти к workspace:

- `crates/heroes_core`
- `crates/heroes_app`
- `crates/heroes_data`
- `crates/heroes_ai`

Но преждевременно усложнять структуру не нужно.

**[ROADMAP.md](./ROADMAP.md)**

Краткие этапы:

| Этап | Цель | Критерий готовности |
|------|------|---------------------|
| 0 | Подготовка репозитория | `cargo run` открывает окно |
| 1 | Чистая игровая модель | `cargo test` проходит без окна |

| 7 | Расширение | Только после готового среза |

## Первые технические решения

### ECS или чистая модель?

Если используется `Bevy`, ECS хорошо подходит для визуального слоя, но доменную модель лучше не растворять полностью в ECS.

Рекомендация:

- игровые правила держать в обычных Rust-структурах;
- Bevy-системы использовать как адаптеры: ввод, отрисовка, UI, синхронизация состояния.

### Координаты

Для старта использовать квадратную сетку:

- `Position { x: i32, y: i32 }`
- движение в 4 направлениях: вверх, вниз, влево, вправо;
- диагонали добавить позже.

### Карта

Начать с фиксированной карты в коде или простом `ron/json` файле.

Не делать редактор карт до вертикального среза.

### Сохранения

Не делать сохранения в первом прототипе. Но структуры желательно проектировать так, чтобы позже их можно было сериализовать через `serde`.

## Definition of Done для фичи

Фича считается готовой, если:

1. Она работает в игре.
2. Для чистой логики есть хотя бы базовый тест.
3. Она не ломает существующую игровую петлю.
4. Код отформатирован.
5. Нет очевидных `panic!`, `unwrap()` и `todo!()` в пользовательском пути, если их можно избежать.
6. Ключевые игровые события логируются (см. ниже).
7. Соответствующие задачи отмечены выполненными в `ROADMAP.md` (см. ниже).

## Команды для разработки

Ожидаемые команды после инициализации проекта:

- `cargo run` — запустить игру;
- `cargo test` — запустить тесты;
- `cargo fmt` — форматирование;
- `cargo clippy` — статический анализ.

## Заметки для будущих агентов

- Пользователь хочет игру в стиле `Heroes of Might and Magic` на Rust.
- Общение с пользователем предпочтительно на русском языке.
- Не пытаться сразу строить полноценный клон HoMM.
- Приоритет — вертикальный срез и минимальная играбельная петля.
- Если нужно выбирать между архитектурной чистотой и играбельным прототипом, сначала довести до играбельного прототипа, но не смешивать критически доменную логику с UI.

### Логирование игрового процесса

Логи — второй инструмент контроля после тестов. По ним должно быть понятно, что происходит в игре, без чтения кода.

**Что обязательно логировать** (уровень `info`):

- старт игры и инициализация карты: размер, количество объектов;
- каждое действие игрока: ход героя, сбор ресурса, найм существ, завершение хода;
- начало и конец каждого боя с указанием сторон и итога;
- каждый ход в бою: кто атакует, кого, сколько урона, сколько осталось;
- победа или поражение.

**Формат сообщений** — читаемые фразы на английском, с контекстом:

```
[ADVENTURE] Hero "Aldric" moved from (2,3) to (2,4). MP: 8 -> 7
[ADVENTURE] Hero "Aldric" collected 150 gold at (2,4). Total gold: 650
[TOWN]      Hero "Aldric" recruited 5 Swordsmen for 250 gold. Army: [Swordsmen x5]
[BATTLE]    Battle started: Hero "Aldric" [Swordsmen x5] vs Neutral [Goblins x8]
[BATTLE]    Swordsmen x5 attack Goblins x8: 25 dmg, 3 killed. Goblins remaining: x5
[BATTLE]    Battle over: Attacker wins. Hero losses: 1 Swordsmen
[TURN]      Day 2 begins. Hero MP restored. Town income: +250 gold
```

**Использовать стандартный `bevy` / `log` макросы:** `info!()`, `warn!()`, `error!()` — не `println!()`.

### Контекст пользователя

- Пользователь **не знает Rust** и не имеет опыта в разработке игр.
- Единственная форма обратной связи от пользователя — **визуальный результат запуска приложения**.
- Не ожидать от пользователя проверки кода, понимания ошибок компилятора или ручного тестирования логики.

### Требования к автоматизации проверок

Поскольку пользователь не может проверять корректность кода вручную, **агент обязан** перед передачей результата:

1. Выполнить `cargo build` — убедиться что проект собирается без ошибок.
2. Выполнить `cargo test` — все тесты должны проходить.
3. Выполнить `cargo clippy -- -D warnings` — не должно быть предупреждений.
4. Выполнить `cargo fmt --check` — код должен быть отформатирован.

Если что-то из этого не проходит — **сначала исправить, потом сообщать о готовности**.

Тесты — главный инструмент уверенности в корректности игровой логики. Любое поведение, которое пользователь не может проверить глазами (правила движения, подсчёт урона, экономика), **обязано** быть покрыто тестом.

## Git-workflow

- **Worktrees не использовать.** Вся работа ведётся в основном рабочем дереве (`C:\Users\rootm\source\heroes_of_rust`).
- **Каждый этап — отдельная ветка.** Перед началом этапа N создать ветку `stage-N` от `master` (или текущей основной ветки) и вести работу в ней.
- По завершении этапа (все чеки зелёные) смёржить ветку в `master`.

Пример:
```
git checkout master
git checkout -b stage-5
# ... работа ...
git checkout master
git merge stage-5
```

## Начало этапа — сначала планирование

Перед тем как приступать к реализации любого этапа, агент обязан **детально спланировать** его и получить подтверждение пользователя:

1. Прочитать текущий этап в `ROADMAP.md` — понять, что уже есть в проекте.
2. Создать отдельный файл `docs/stage-N-plan.md` с подробным планом этапа:
   - что уже есть в проекте и что будет добавляться;
   - конкретный список задач с чекбоксами;
   - новые модули, структуры, файлы которые появятся;
   - что остаётся в `ROADMAP.md` без изменений и что будет уточнено.
3. Представить план пользователю и дождаться его подтверждения.
4. Только после подтверждения — перенести детали в `ROADMAP.md` и переходить к написанию кода.

Файл плана хранится в `docs/` и не удаляется после этапа — служит историей решений.

Планирование этапа может выполнять отдельный агент-плановщик — не обязательно тот же, кто будет писать код.

## Ведение ROADMAP.md — обязательно

После выполнения каждой задачи агент **обязан** обновить `ROADMAP.md`:

- Выполненная задача: `- [ ]` → `- [x]`
- Этап полностью завершён: добавить `✅` к заголовку этапа
- Этап в работе: добавить `🔄` к заголовку этапа

Это нужно делать **в том же ответе**, в котором выполняется задача — не откладывать на потом.

Пример:
```
- [x] Выполнить `git init`
- [x] Выполнить `cargo new heroes_of_rust --bin`
- [ ] Проверить актуальную версию Rust...
```
